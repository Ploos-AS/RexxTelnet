# M2 — Interactive terminal baseline

## Delivered

M2 introduces a terminal layer that remains independent from the Telnet parser and session transport.

- host-testable terminal state machine
- plain text pass-through
- ANSI/VT100 CSI parsing baseline
- fragmented escape-sequence handling
- terminal dimensions tracked in session state
- Telnet NAWS payload generation
- required IAC escaping inside NAWS payloads
- Amiga console backend using DOS `CON:`

## ANSI/VT100 scope

M2 establishes CSI parsing and state retention across fragmented reads. Rendering policy is intentionally minimal at this stage; later milestones can map parsed commands to richer terminal behavior without changing the byte-stream API.

The parser recognizes numeric CSI parameters and final command bytes. This is enough to support SGR/cursor/erase families incrementally.

## NAWS

The terminal core can construct RFC 1073 NAWS subnegotiation from real terminal dimensions. Embedded byte value 255 is escaped according to Telnet framing rules.

NAWS advertisement remains a session-policy concern: the payload is available when the peer negotiates option 31 and the terminal layer has dimensions.

## Amiga backend

The initial interactive backend opens an AmigaDOS console window via:

`CON:0/0/640/200/RexxTelnet/CLOSE/WAIT`

This is deliberately simpler than an Intuition-native custom terminal. It gives the project an Amiga-native keyboard/output path while preserving minimum-spec compatibility and keeping the protocol core testable on the host.

## M2 acceptance

- terminal parsing is independent of AmigaOS
- fragmented CSI sequences are preserved correctly
- text bytes are emitted unchanged
- NAWS payloads are correct and Telnet-safe
- an Amiga console I/O backend exists
- M0/M1 tests remain part of `make check`
